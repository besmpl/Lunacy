## Selection and convergence

The supplied top three are **budget-5** (7.15), **inversion-1** (6.85), and
**budget-1** (6.65). They are hypotheses only. Source reconciliation changes
what they mean:

1. **budget-5 is already largely present.** `tests/test_usage_report.py`
   exposes 23 ordinary methods (`:110-493`), and the standard unittest loader
   already accepts a fully qualified method selector. No missing runner seam is
   demonstrated.
2. **inversion-1 is not present, but is an unproven new output convention.**
   Existing failures already contain unittest traceback/assertion context; the
   source does not own a stable fixture argv for every method. Emitting one
   risks becoming a new mode/protocol and cannot repair a wrong expectation.
3. **budget-1 could improve local wording, but evidence only shows wrong
   semantics, not a repository-wide unit-label omission.** Applying it broadly
   would be a new convention without measured rework reduction.

The remaining high-scoring proposals have the same issue: receipts and raw
exits are already required; a capsule/parser/monitor/ledger/acceptance replay
would add state or authority; fixture metadata risks making the oracle
self-referential; and the Git-status probe was incidental rather than product
behavior. No selected idea survives source checking as a demonstrated,
material, net-simplifying product or workflow seam.

## Focus paths

### Focus 1 — qualified edge-case reruns as normal unittest methods

**Sketch.** Use the existing named methods as the sole selector for a focused
rerun, preserving the ordinary unittest process, raw stdout/stderr, and exit.
No new selector vocabulary, acceptance replay, or fixture convention is added.

**Risk.** Shared mutable fixture state or environment-dependent Git data could
make a method appear isolated; a qualified name is not proof of deterministic
setup or a correct oracle.

**First step.** Source-check the current methods and map each cycle20 edge case
to an existing method; do not edit fixtures or acceptance behavior until a
missing method is demonstrated.

**Children.** Name-driven routing; minimal fixture per method; raw failure
bundle; acceptance replay (rejected because unconditional replay conflicts
with existing acceptance/ownership rules).

### Focus 2 — assertion-owned shell-safe repro argv

**Sketch.** Generate a copyable argv at a failure seam so the parent does not
rebuild a probe. This is attractive for heredoc mistakes but requires every
fragile test to retain canonical setup metadata and introduces a convention
that the source does not currently promise.

**Risk.** An argv can omit temporary fixture state, path context, interpreter
selection, or environment and create false confidence; shell quoting itself
becomes another contract.

**First step.** Inventory methods and their setup before proposing any formatter;
stop if no common owner exists. No source edit is justified in this cycle.

**Children.** Explicit selector/fixture vector; bounded observed/expected
counts; one copy-paste line; quote round-trip test. All remain future options.

### Focus 3 — unit-bearing boundary assertions

**Sketch.** Add labels such as “bytes” or “records” only to existing ambiguous
assertions while retaining direct comparisons. This is the smallest possible
source change if a real ambiguity is found, but the current source inspection
has not found a shared assertion seam, and the examples include incorrect
expectations rather than merely unlabeled values.

**Risk.** Message-only edits cannot fix a wrong manifest-cap fixture, a 508 vs
512 contract misunderstanding, or an incidental Git-status slice; a helper
could obscure normal unittest locations.

**First step.** Source-check the affected assertion sites and identify an
actual repeated ambiguity before any wording change. No implementation is
adopted here.

**Wildcard (verbatim worker-authored).** If the next failing message already named its unit and owner, would the remaining worker-parent loop reveal that the true missing abstraction is runner ownership rather than assertion clarity?
