# Executable import-service workload — public contract v2

## Outcome and scope
A local Python-standard-library customer import service accepts JSON and CSV through its maintained CLI and WSGI HTTP adapter. Every adapter must preserve the shared validation result and import atomically. Provide migration guidance for callers. This is one unsplit product outcome, not a role/ready-work graph. No network server or external service is required: exercise WSGI through its ordinary request callable and streams. Later supplied raw input observations obey these same rules and introduce no new API or requirement.

## Shared data and parser
Rows have exactly the public fields id, email, display_name. id must be a nonempty string after stripping outer whitespace. email must be a string whose stripped value is nonempty, contains one @ with nonempty sides, and has no internal whitespace; normalized email is stripped/lowercase. display_name is a string preserved exactly, including embedded CR, LF, commas, double quotes and Unicode. Extra input fields are ignored. IDs are case-sensitive. Duplicate normalized IDs within a batch are invalid; all occurrences after the first get DUPLICATE_ID. Empty batches are valid.

`core.parse.parse_records(payload: str, format: str) -> dict` is the fixed public parser seam. format is json or csv. JSON is an array of objects; CSV has a header containing id,email,display_name once each (extra columns allowed), and standard csv quoting/newlines. Invalid encoding is handled at the transport boundary. Structural/format syntax failure returns records=[] and errors=[{row:0,code:'INVALID_INPUT'}]. Otherwise return records for individually valid rows in input order and errors for invalid rows, one error per invalid row, in input order. Row numbers are 1-based data-record indices, not physical source lines. Field validation precedence: INVALID_ID, INVALID_EMAIL, INVALID_DISPLAY_NAME, then DUPLICATE_ID. Duplicate tracking uses the first otherwise valid occurrence; an invalid row does not reserve its id. No hidden input mutation. The presence of records alongside errors is deliberate preview information, NOT authority to commit a partial batch. Tests must use actual parser outputs, not a parallel invented parser.

This parser is supplied complete; worker task may repair other source as necessary but must preserve this public contract. No claim that a filename or current implementation is an access/write whitelist; ownership is decided in actual native assignments, not pre-split here.

## Persistence and shared import
`core.store.list_customers(db_path) -> list[dict]` returns current rows sorted by id; a missing database is empty without creating it. `core.store.commit_customers(db_path, records) -> None` atomically upserts this already-validated batch by id using SQLite; existing other rows remain. Store helper is supplied correct. Runtime I/O failures propagate rather than success-shaped fallback; this fixture does not require fault-injected OS-crash durability.

`service.import_customers(db_path, payload: str, format: str) -> dict` calls the actual parser and returns exactly {status:'ok', imported:N} if errors is empty, committing all normalized records through store. If errors exists, return exactly {status:'invalid', errors:[...]} and do not call commit: no database creation, modification or partial import. Historical stores and reports are preserved unless the caller authorizes that exact new batch. Result says what this call did, not current proof adequacy or acceptance.

## CLI
Maintained entry: `python -B cli.py --database PATH --format json|csv --input PATH`.
Read the entire input as strict UTF-8 bytes -> text WITHOUT newline/Unicode-separator rewriting. Write exactly one JSON result plus LF to stdout. Success exit0; validation/structure/invalid-UTF8 exit2 with status invalid (UTF8 errors use row0 INVALID_INPUT). No success-looking text or extra stdout. Under invalid input the database is unchanged (or remains absent). Unexpected I/O errors must be nonzero and not emit a status ok result; no exact stderr spelling is required. CLI JSON whitespace/key ordering is not significant; response data and terminal status are.

## WSGI HTTP
Maintained `http_api.application(environ, start_response)` uses environ['lunacy.database'] for the caller-owned database path. Supported request: POST /imports, CONTENT_TYPE application/json or text/csv, optional `; charset=utf-8`, CONTENT_LENGTH a valid nonnegative decimal byte length, wsgi.input a binary stream. Read exactly CONTENT_LENGTH bytes using bounded reads (short reads may require more than one read); premature EOF yields INVALID_INPUT. Do not read beyond the declared body. Decode strict UTF-8 with original text/newline contents. Call actual service. Return a one-element bytes list containing JSON result plus LF; Content-Type application/json; Content-Length exact returned-byte count. Success200 OK; invalid data/UTF8/length/premature EOF400 Bad Request. Unsupported path/method/content type returns404 Not Found/405 Method Not Allowed/415 Unsupported Media Type respectively with {status:'error', code:'NOT_FOUND'|'METHOD_NOT_ALLOWED'|'UNSUPPORTED_MEDIA_TYPE'}, no persistence effect. Precedence path, method, media, then body/validation. Invalid-body result is the same row0 INVALID_INPUT form. Unexpected I/O error must propagate, not fabricate a200 response. No sockets, live server, threads or outbound requests are needed to exercise this actual WSGI seam.

## Boundary clarifications before authorship
CSV uses Python standard-library excel dialect with strict syntax parsing and original newline text. Header names are exact/case-sensitive, not stripped; required names occur once. An empty CSV file, duplicate required header, syntax error, or any data-row width differing from the header width makes the whole input structurally invalid (row0 INVALID_INPUT, no records). Extra named columns are ignored. Header-only CSV and JSON [] are valid empty batches. A JSON array containing a non-object member is structurally invalid as a whole; missing/wrong-type fields inside an object use per-row field precedence. Duplicate JSON member names use normal json.loads behavior; no separate rejection policy is requested.

HTTP CONTENT_LENGTH is a nonempty ASCII digit string with no sign/whitespace; missing or other spelling is invalid. Media type and the optional charset value are ASCII-case-insensitive, with optional ASCII whitespace around tokens/semicolon/equals; the only allowed parameter is one charset=utf-8 (no quoting/additional/repeated parameter). Transport metadata are strings and wsgi.input is an ordinary binary readable stream; exotic types are not a requested fuzz domain. Path/method checks remain exact. Public error dictionaries and error-list order are exact; JSON serialization layout is not. No OS-crash or hostile-writer guarantee is implied.

## Explicit v2 runtime and historical-store boundaries

This bounded fixture uses Python's standard-library CSV reader with its unmodified default field-size limit of 131072 decoded Unicode characters per CSV field, inclusive. The limit applies to header fields and ignored extra fields as well as the three required fields; embedded CR and LF count as their individual preserved characters. A larger CSV field is structural INVALID_INPUT. This is not an input-byte limit and does not impose a new JSON field-size limit. An interpreter whose ambient csv.field_size_limit() differs from 131072 is outside this fixture's tested runtime, not a candidate behavioral failure; the fixed evaluator must report that environment prerequisite as ERROR. Do not change process-global CSV settings to satisfy the fixture. If larger CSV fields or arbitrary host CSV configuration becomes required, replace this bounded parser/runtime contract and corresponding tests deliberately; do not silently widen the claim.

Historical databases use the existing SQLite table schema `customers(id TEXT PRIMARY KEY, email TEXT NOT NULL, display_name TEXT NOT NULL)`. Preserve this compatibility seam and existing caller-owned SQLite constraints and triggers: do not drop/bypass them or migrate storage to evade a rejected write. A valid batch may still fail during persistence; if a later row is rejected by SQLite, propagate that error and roll back the whole batch so earlier writes from that batch do not survive. No particular trigger name or rejection value is required; those are caller-owned database facts. This adds no OS-crash durability or hostile-writer guarantee.
