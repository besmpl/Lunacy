# Native parent planning and acceptance

## Adoption and material change

Astra is the preferred actual parent when host/user authority selects it; never spawn a shadow parent or infer model identity from prose. Seal the complete observable outcome, architecture, affected maintained scope, ownership, exact route, required verification, acceptance standard, permitted effects, and relevant rules in one immutable TASK adoption or one exact immutable plan reference containing them all. A supplied plan may be adopted only after judging authority, restrictions, capabilities, effects, and feasible proof together. Missing material facts justify one bounded discovery question, not compulsory clerical drafting.

Resolve hard decisions in this order: explicit current user intent; project ethos and goal; adopted architecture/contracts; established evidence; conservative engineering judgment. Record consequential conclusions in immutable TASK decisions. Material scope, architecture, route, effects, or acceptance change requires a new adoption before affected work resumes and stales relevant proof. Continue unrelated work only when separately authorized and demonstrably independent. Proposal-only work remains confined to its named authorized paths.

## Exact native routing

Select and persist exactly one immutable model binding before dispatch. The named defaults remain exactly: `luna` = `gpt-5.6-luna`/`max`; `sol-medium` = `gpt-5.6-sol`/`medium`; explicitly selected `sol-high` = `gpt-5.6-sol`/`high`. The user-directed task-shape policy remains: Luna/max for bounded bulk work with cheap independent checks; Sol/medium for judgment-heavy implementation, discriminating test design, or difficult diagnosis; explicitly selected Sol/high for especially consequential bounded judgment. This is not a measured superiority claim. There is no universal file-count threshold or superiority claim. As the only alternative, current user/project authority may explicitly authorize an exact native model **and** exact effort for the stated worker purpose. General interest in cheaper, better, or latest models; a parent preference; a model catalogue entry; host availability; or selection/mention of a model for consultation does not authorize that model for an implementation worker. Record the resolved literal model and effort plus exact authorizing source in the adoption and immutable Authorized Assignment before dispatch—even for a named default—not in a mutable alias, ambient default, catalogue, or reference. Later preset, default, or catalogue changes cannot alter that sealed assignment. A named default plus a conflicting explicit pair is a conflict: refuse rather than choose precedence or normalize it. Recheck current authority before dispatch; later restrictive user/project input blocks the affected dispatch and requires a new adoption rather than silently rewriting or substituting the sealed pair.

Dispatch only when the actual host creation tool can preserve the adopted literal pair through one of two exact routes: pass supported model **and** effort creation parameters explicitly, or select a fixed role whose current supplied creation-tool definition fixes **both** values to that exact pair. Give the worker the same literal pair, context, owned scope/effects, report path, and attempt/recovery entitlement. A role name, role configuration file, catalogue label, old receipt, request, or assignment text alone is not a route guarantee; a model-fixed but effort-inherited role is insufficient, and no worker-local string can override the host definition. If the current tool definition or route is unavailable, ambiguous, conflicting, unsupported, or cannot preserve the pair, refuse the affected dispatch. Do not infer an effort, repair or normalize a pair, override a fixed role to change it, probe a different model, silently fall back, or use custom-role substitution to a different pair; selecting an exact fixed role matching the sealed pair is not such substitution. Configuration, a request, or an assignment is not independent backend attestation. The first real authorized dispatch is the capability observation; never launch a dummy trial or alternate route.

Use a fresh child context by default. An exact justified inheritance exception belongs in the adoption/decision and may alter only context inheritance. Every dispatch requires the preexisting immutable Authorized Assignment; it is authority to act, not launch evidence, and never contains an invented future handle or `LAUNCHED` fact. After creation returns, record the actual handle and launch observation in mutable TASK coordination. A missing or ambiguous return stays UNKNOWN/OPEN possible custody and grants no retry, replay, replacement, fallback, or renewed entitlement. Never change the pair of a live or unknown-effect same-surface attempt. A route change requires its ownership/effects to settle, a new adoption, and a fresh authorized assignment/attempt; old attempt budgets, history, contract, model, effort, and effects remain unchanged. Unrelated old OPEN work does not globally block demonstrably independent, explicitly authorized work on different established-independent surfaces. Same-agent substantive post-FINAL continuation requires a new authorized assignment/report and follows the fresh-context default; the shared report-only correction rule requires no worker continuation.

## Dispatch and evidence ownership

Before dispatch or continuation, inspect TASK current coordination, adoption, and the preexisting Authorized Assignment, then compare same-root ACTIVE and retained/ambiguous BLOCKED ownership across known workflows. Reconcile current service/entry, competing surfaces, reservations, attempts, and effects. Unknown release or missing FINAL never permits replay. Form the maximal safe batch only from independent authorized work and give each surface/effect one owner. Shared work gets only necessary TASK rows for actual ownership, dependencies, and barriers.

A handoff names current project rules, exact TASK adoption/assignment anchors, applicable shared [WORKSPACE.md](../WORKSPACE.md) sections, [ENGINEERING.md](../worker/ENGINEERING.md), and only the specific parent-planning sections required for the assigned action, plus owned scope/effects and exact absolute report/log/output paths; this whole guide is not a default worker prerequisite. Resolve a recurring path once and repeat the same absolute value. Require affected-behavior discovery, maintained caller/reuse/test tracing, end-to-end implementation, ordinary repair, final diff review, terminal verification, and escalation before overlap or material expansion. Do not duplicate complete inventories when exact references are unambiguous.

For a once-per-session duty, reuse an established receipt only when evidence covers the applicable session; follow the duty on a confirmed uncovered session. Unknown coverage requires resolution before affected dispatch, neither omission nor repetition. Carry no invented platform session semantics.

Name permitted direct/indirect effects, owners, operation bounds, and feasible settlement evidence before dispatch; record actual handles only when created. Permission to use an OS API does not map an opaque tool handle to an OS group. Evidence proves only its observed boundary and cannot waive stronger required proof, retry rules, or newly discovered writers/effects.

Evidence ownership is finite. Apply the canonical [shared finalization policy](../WORKSPACE.md#worker-updates-and-immutable-report) and [parent acceptance rule](../WORKSPACE.md#ownership-barrier-and-acceptance): the worker tests the final artifacts and reports actual results; an adversary exists only for one named material risk and a scout only for useful read-only compression; the parent independently reviews the actual result and executes proof only for the named triggers. Do not duplicate broad proof merely because the verifier differs.

Any required matrix, live check, or independent repetition remains required and is assigned to one layer. Evidence is reusable only while the claim-relevant artifact, dependencies, configuration, environment, and scope still match; changed inputs stale affected verification.

## Acceptance and barrier

Before closure, reread current authority and TASK, reconcile all actual workers, commands, sessions, effects, reports, and owned surfaces, and inspect the integrated result against the whole adoption. Keep the barrier OPEN for any active or uncertain writer/effect. PASS and FINDINGS require established quiescence and CLOSED; unknown authority, freshness, custody, or effects requires BLOCKED/OPEN with the retained owner and bounded next action. Terminal text, timeout, stdout, hashes, or current process listings never manufacture release.

Only the parent accepts. It applies the shared finalization policy, independently inspects actual code/diff/behavior and evidence coverage, performs proof when that policy requires execution, reconciles worker reports to their assignment anchors, actual handle observations, and effect custody, then appends an immutable TASK acceptance. Every request is satisfied, explicitly superseded, or authoritatively deferred. Required live evidence remains live; prose scenarios do not prove route/model obedience, custody, effects, or correctness. Substantive findings or product repairs need a new attempt. Preserve finalized reports and old acceptances; a receipt-supported clerical report correction instead follows the shared report-only rule. A contract disagreement is a finding/decision, not invented custody uncertainty.

## Adopted deadlines and finalization

This section applies only when authority adopts an overall task deadline. Otherwise do not invent one; commands and sessions still have finite bounds and recovery clocks. At adoption, reserve a named finalization interval sufficient for custody reconciliation, TASK update, and parent acceptance. If the budget cannot contain them, expose the conflict rather than dropping proof.

The reserve start is the implementation cutoff. After it, start no implementation, repair, replacement, checkpoint cycle, provider operation, or new task effect. Only bounded finalization actions remain: settle/interrupt owned handles, complete already-required verification/reconciliation, and update TASK. This never authorizes re-entry or retry.

Before any potentially blocking finalization wait, write one durable TASK coordination update naming actual live owners, custody/proof uncertainty, OPEN barrier, and one safe next action. Do this once for the current facts, not as duplicate pre-wait ceremony. Later evidence supports a new current update and, only when ready, acceptance; do not pre-author future acceptance pointers. Deadline pressure cannot create CLOSED, PASS, or released effects.

## Recovery and anti-stall

On restart, read current rules, authority, TASK, and only evidence required by its next action. Never reconstruct authority from chat or bulk history. Recovery applies only before an adopted implementation cutoff; a shorter cutoff grants no retry or shortcut.

For genuinely new work, the Authorized Assignment may pre-adopt one optional earlier initial-silence threshold. The assignment itself must state the threshold, the observable parent event used as its clock anchor, the clock basis, and the parent-visible observation scope. The anchor is an evidenced observable parent event, never an inferred provider or backend start. Do not add a mandatory ledger, stage, acknowledgement, preliminary artifact, token file, or default numeric threshold. If this policy is absent, its anchor or required clock evidence is unavailable or unestablished, or an earlier overall implementation cutoff arrives first, preserve the uncertainty and use the existing recovery/cutoff rules rather than inventing elapsed time.

The earlier threshold may advance only the first lifecycle inspection for that assignment. It applies only until **any qualifying substantive parent-visible evidence** is actually received, whether or not it is the expected evidence; a verified FINAL may be the first such evidence. Qualifying evidence identifies changed owned work with substantive evidence, a running bounded command and its custody, or a terminal result with enough evidence to reconcile. Narrative activity, bare assertions, metadata/no-op churn, irrelevant reruns, weakened acceptance, or mandatory-interim-artifact theatre do not qualify. No qualifying evidence observed is not proof that no work occurred, and late visibility must preserve that distinction. Once qualifying evidence arrives, the initial-silence rule is permanently inapplicable to that assignment; it does not reset any clock or attempt fact.

At the evidenced earlier threshold, inspect owner lifecycle once. If active and the attempt's single challenge is unused, use the existing 5-minute checkpoint challenge and mark it consumed; if active and that challenge is already consumed, do not reissue it and take the first applicable existing later recovery row; if terminal, reconcile custody. Do not add a challenge, renewal, replacement, fallback, replay, or interruption right. The conditional one renewal or pre-authorized named-operation deadline, interruption judgment, retained UNKNOWN/OPEN custody, and ordinary 15-minute no-action recovery remain unchanged. A challenge or renewal already consumed under any applicable contract stays consumed.

For one exact attempt, take the first matching action in one parent turn; absent an applicable earlier initial-silence inspection, the 15-minute observation remains the default:

| Observation | One bounded action |
|---|---|
| 15 minutes without an actionable attributed event, while this attempt's single challenge is unused | Inspect owner lifecycle once. If active, send that one checkpoint challenge, mark it consumed, and start a 5-minute response clock; if terminal, reconcile custody. If the challenge is already consumed, this row is inapplicable and the first matching later row governs. |
| Substantive checkpoint before expiry | Grant at most one 15-minute renewal if unused, or honor one pre-authorized named-operation deadline; neither repeats. |
| No valid reply, or renewal/deadline expires | Judge plausibility, then interrupt the current owner once. Do not accept, retreat, or replace yet. |
| Every same-surface owner terminal and effects proven settled | Inspect freshness and acceptance; if incomplete, narrow/retreat or consider one new attempt only after recording sealed remainder, failed tactic, revised/forbidden tactic, and fresh basis. |
| Any authority, overlap, ordering, custody, effect, or freshness fact unknown | Keep BLOCKED/OPEN and return parent decision; do not replace or replay. |

Persist `attempt; challenge=consumed; renewal=unused|used; deadline=...` in TASK current recovery. Resume, identity/model changes, irrelevant events, or rephrasing do not reset clocks. If recovery facts are absent or stale, require parent decision instead of recreating entitlement.

A valid checkpoint identifies a changed owned artifact/symbol with substantive evidence, or a running bounded command and its custody, plus uncertainty and next boundary. Narrative activity, metadata/no-op churn, irrelevant reruns, weakened acceptance, or bare passing claims are invalid. Late/duplicate replies are historical evidence only.

Interruption and lifecycle terminality do not prove settlement. Replacement requires every same-surface owner terminal, effects settled, and a materially different tactic or cited changed fact/current renewal. A new identity alone is not fresh. Unknown provider/effect entry is never safe to retry. Preserve useful work and frozen evidence.
